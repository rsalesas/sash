Sash

A Swift package that makes a single-page web app feel like a native macOS app. Brainstorming notes, September 2026.

One sentence. The SPA stays a plain web app that talks HTTP. Sash owns a private URL scheme inside a WKWebView and decides who answers each request: files in the bundle, Swift handlers in-process, a local socket, or a real server. Everything native — window, toolbar, Settings, storage, updates — comes from Swift the developer writes, with Sash doing the wiring.

Where this comes from

Vaelth.app is a native shell around a portal served by a Go daemon. It hosts the unchanged SPA in a WKWebView under a private scheme, proxies every load to the daemon's unix socket (including two Server-Sent Events streams), watches the DOM to drive a native toolbar, runs the daemon's doctor and repair from a SwiftUI Settings pane, and updates itself from an appcast with a SHA-256 and code-signature check before swapping the bundle in place.

Compared with Tauri, it is the same shape: thin native process, system web view, custom scheme, in-place updater. It differs where it matters here. Tauri's custom protocol returns a whole response and cannot stream, so SSE over it does not work. Tauri has native menus and a tray but no NSToolbar items. Tauri's job is cross-platform; this shell's job is to be a Mac app.

Sash is the generalisation: keep the parts that were about hosting a web app well, drop the parts that were about vaelth, and make the transport pluggable.

The core idea

The SPA does fetch("/api/...") and new EventSource("/events") and nothing else. Sash routes each request to a source:

  • Bundle source. Files embedded in the app or package, served with correct MIME types. This is the zero-backend case: a world clock, a note taker, a calculator.
  • Swift routes. Handlers registered from Swift. Bodies are async sequences of bytes, so a route can stream and SSE works exactly as it does in Vaelth.app today.
  • Socket or remote source. A unix socket (what vaelth does) or an HTTPS origin behind an allow-list, for the mixed online-and-local case.
  • Overlay source. An updated web layer in Application Support layered over the shipped one. This is how the inside changes without the app changing.

Because the contract is HTTP, the same SPA runs unchanged against a real server in a browser, against a mock in tests, and against Swift in the app. That is the property that makes it friendly to AI-written code: the model writes an ordinary web app and an ordinary set of handlers.

// Sketch, not an API
let app = Sash.App(bundle: .module) {
    Routes {
        Get("/api/clocks") { req in try await Clocks.list() }
        Stream("/events") { emitter in
            for await tick in Clock.ticks { emitter.send("tick", tick) }
        }
    }
    Storage(.userDefaults(suite: "app.sash.worldclock"))
    Updates(app: .appcast(url), web: .manifest(url, publicKey: key))
}

What the package has to provide

Bridge, both directions, but boring

  • Page to app. window.host.call(name, args) returning a promise, built on WKScriptMessageHandlerWithReply. Named, typed, and listed, so the capability surface is enumerable.
  • App to page. The events stream. The page needs no special code to receive pushes; it is already an EventSource consumer.
  • Observe mode. The DOM-watching context bridge from vaelth becomes an opt-in for SPAs you are not allowed to modify: a user script reports the active view, title, and subtitle.

Storage as a first-class citizen

  • Custom-scheme origins have had unreliable localStorage persistence, and service workers do not run on them at all. Do not rely on WebKit here.
  • Inject the whole store as a user script at document start and shim localStorage over it, with writes flowing through to UserDefaults or a file. Synchronous semantics preserved; data lives where a Mac app's data lives.
  • Alongside that, an async host.storage for Keychain, iCloud key-value store, and files, for apps designed for Sash rather than merely hosted by it.
  • This is the piece with real WebKit risk. Prototype it first.

Two update channels, independently versioned

ChannelMechanismGuards
App bundle Appcast manifest, download, in-place swap, relaunch. Lifted from Vaelth.app's updater. SHA-256 must match the manifest; the new bundle's code signature must validate. Swapping a bundle ourselves bypasses Gatekeeper, so the updater does Gatekeeper's job.
Web layer Signed manifest of files with hashes, downloaded into an overlay directory, switched in atomically on next load or live reload. Ed25519 signature verified with a key embedded in the app (Gatekeeper never sees HTML). The manifest declares the Swift API version range it needs. The page must call host.ready() within a few seconds of boot or the overlay is rolled back to the shipped bundle.

A release can move either channel or both. The compatibility range is what keeps a web-only update from calling a route the shipped Swift does not have.

Native chrome from declarations

  • Toolbar. Items, primary action, and window title set by the page via host.toolbar.set([...]), or read from the DOM in observe mode.
  • Settings. A SwiftUI Settings window where UserDefaults is the source of truth. Both sides subscribe; changes reach the page over the events stream.
  • Defaults that are not optional. A real Edit menu (a WKWebView is mute on cut, copy and paste without one), window restoration, appearance sync, and an About panel.

Security by construction

  • The page has no origin any other page could share and no route to the network except sources the Swift side registered.
  • Routes and host calls are the whole capability surface, so the permission story is the list of routes.
  • Navigation policy denies anything outside the scheme; external links open in the default browser.

Dev and test loop

  • A dev source that proxies / to Vite with live reload while /api still hits Swift.
  • A flag that also exposes the Swift routes on localhost so the SPA can be opened in Safari with real devtools.
  • The offscreen WKWebView self-check from vaelth becomes an XCTest helper that boots the shell headless and asserts the page reached ready.

What lifts out of vaelth, and what does not

Lifts with light generalisationStays behind as product code

  • NSException bridge for the torn-down WKURLSchemeTask race
  • HTTP-over-unix-socket client
  • App updater and update checker
  • Offscreen self-check harness
  • DOM context bridge (as observe mode)
  • Toolbar chips and their layout
  • Daemon monitor (becomes a source-health hook)
  • Doctor and repair, elevation flow
  • Anything that knows what a host or a route is

New work: the storage shim, the signed web-layer overlay with rollback, the route DSL, and the dev proxy. None is large.

Gotchas already paid for

  • WKURLSchemeTask can be torn down while a callback is in flight. A stopped flag under a lock handles the common case; an Objective-C exception bridge covers the window no lock can close. wry, Tauri's web-view layer, does the same with objc2::exception::catch.
  • The page reads location.host. Pick an authority for the private scheme that keeps that sensible.
  • A WKWebView outside a window does not load. Tests need an offscreen window.
  • Two artifacts, two version numbers. The app and the web layer must not share one pointer on the CDN.
  • Ordering of privileged and unprivileged setup steps matters when they create shared directories. Sash will not ship elevation, but the lesson applies to any app that does.

Phasing

  1. Shell. Bundle source, routes, events, storage shim, Edit menu, window restoration. Ship the world clock as the example app.
  2. Updates. Both channels with rollback, plus the compatibility range between web layer and Swift API.
  3. Ergonomics. Toolbar and Settings bridges, dev proxy, test helper, and two skills: one for the Swift side and one for the SPA contract, plus a template repo.

Open decisions

  • The exact JavaScript surface of window.host, and whether it is injected or imported.
  • Whether Swift routes use an existing server type or a tiny one of our own.
  • Where the overlay directory lives and how many versions are kept for rollback.
  • Whether observe mode is worth keeping once the declarative toolbar exists.
  • Minimum macOS version, which decides whether WKWebsiteDataStore(forIdentifier:) is available as a second storage option.
