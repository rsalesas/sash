Sash

Specification, draft 3, matching milestone 1 as built. A Swift package that hosts a single-page web app as a native macOS app: your SwiftUI, your windows, your menus; the web app in a view; extensions as the only door between them. See brainstorming for where this came from.

1. Purpose and scope

Sash makes a web app a good citizen of macOS without pretending to be a cross-platform framework. The developer writes a normal SwiftUI app and a normal single-page web app. Sash supplies the view that hosts the page, the private scheme that serves it, the store that both sides share, and the registry through which Swift grants the page capabilities one at a time.

  • In scope. Hosting, serving, streaming, state, the call bridge, context reporting, many simultaneous web views, a standard set of extensions, two update channels, a test harness, and skills that teach an AI both halves of the contract.
  • Out of scope. Windows and Linux. A JavaScript UI framework. Anything that makes the page reach the operating system without a Swift declaration.

Design rule. The page talks HTTP and a small JavaScript object. Swift decides who answers. Nothing the page can reach exists unless Swift declared it.

2. Concepts

TermWhat it isCardinality
Host An @Observable reference type owning the registry, the store, the sources, and the list of live sessions. Created once, usually in the App. One per app, more if you want isolated worlds.
Session One WKWebView plus its context, its events stream, and its per-session extensions. Has an id and an entry route. As many as you like. One per SashView.
SashView The SwiftUI view. An NSViewRepresentable that creates a session on appear and ends it on disappear. Takes a host and an optional route. Anywhere a view goes.
Source Answers requests for the web layer's files: bundle, overlay, socket, remote, dev. One chain per host.
Extension A Swift type that declares calls, routes, streams, and scripts under a namespace, and hooks session lifecycle. Installed per host; instantiated per host or per session by its scope.
Store The shared key-value state, Codable values, scoped by name, with pluggable persistence. Backs sash.state, the localStorage shim, and Settings. One per host.
Context What a session's page is showing: title, view id, selection, dirty, commands it can handle. Observable from Swift. One per session.
@main struct WorldClock: App {
    @State private var host = Sash.Host(web: .bundle(.module)) {
        Net(allow: ["worldtimeapi.org"])   // standard, opt-in
        Clipboard()                         // standard, opt-in
        Clocks(store: db)                   // the app's own extension
        Alerts()                            // the app's own: page asks, Swift notifies
    }

    var body: some Scene {
        WindowGroup {                                   // main window
            SashView(host)
                .toolbar { ClockToolbar(context: host.focused?.context) }
                .navigationTitle(host.focused?.context.title ?? "World Clock")
        }
        WindowGroup(for: Sash.Route.self) { $route in   // windows your extensions open
            SashView(host, route: route)
        }
        Settings { ClockSettings(settings: host.store.scope("settings")) }
        .commands { ClockCommands(host) }
    }
}

3. The web contract

Everything the page can do is one of four things: fetch a URL, open an events stream, call a declared function, or read and write shared state. The global is window.sash.

3.1 Origin and paths

  • The page is served at sash://app/. The scheme is private to the process; the authority is fixed so location.host is stable.
  • /_sash/* is reserved for the framework. Everything else belongs to the developer's sources and routes.
  • Route handlers registered from Swift take precedence over the source chain, so /api/... can be Swift while / is the bundle.
PathPurpose
/_sash/eventsThe per-session Server-Sent Events stream. Named events; JSON data.
/_sash/stateBulk read of the store scopes the page may see, used at boot by the shim.
/_sash/capabilitiesThe installed namespaces and their calls, as JSON. Same data the JS table is generated from.
/_sash/sash.jsThe runtime the page may import explicitly. It is also injected as a user script, so importing is optional.

3.2 Calls

One WKScriptMessageHandlerWithReply named sash. A message is { id, ns, name, args }; the reply is { ok, value } or { ok: false, error: { code, message, data } }. The generated table turns that into await sash.haptics.perform({ pattern: "levelChange" }). Arguments and results are JSON; Swift handlers see Codable types.

Error codes are fixed: capability-missing, invalid-args, denied, unavailable, failed. A call into an uninstalled namespace rejects with capability-missing; it is never undefined.

3.3 Events

The page opens new EventSource("/_sash/events"), or uses sash.on(name, fn) which does the same. Swift pushes with session.emit(name, payload) for one session or host.broadcast(name, payload) for all. Framework events are prefixed sash:; developers own the rest of the namespace.

EventWhen
sash:stateA store key changed, from Swift or from another session. Carries scope, key, value.
sash:appearanceLight/dark, accent colour, or reduced-motion changed.
sash:focusThis session's window gained or lost key status.
sash:commandA menu or keyboard command the page declared it handles.
sash:capabilitiesAn extension was installed or removed after load.
sash:terminateThe app is about to quit. Flush now.
sash:messageAnother session sent this one a message.

3.4 State

sash.state.get(scope, key), set, remove, watch. Synchronous reads against a local mirror hydrated at document start; writes are applied locally and forwarded, so the page never waits. localStorage is shimmed onto the "local" scope. Settings live in the "settings" scope. Which scopes a page may see is declared on the host.

3.5 Context

sash.context.set({ title, subtitle, view, selection, dirty, commands }). Partial updates merge. Swift reads session.context as an observable struct. The commands array names the sash:command identifiers this view will handle, which is what enables the matching menu items.

3.6 Session identity

sash.session exposes { id, route, isFocused }. The entry route is also the page's location.pathname, so an SPA router needs nothing special.

4. Sessions and many web views

A host may have any number of live sessions. Three windows of the same page, a main window and an inspector, a sheet with a form, a hidden worker session running background JavaScript: all sessions, all equal.

4.1 What is shared and what is not

Shared across sessionsPer session
  • The store, so localStorage in one window is visible in another after sash:state
  • The source chain and route table
  • Host-scoped extensions
  • One WKWebViewConfiguration and scheme handler, so WebKit shares processes where it can
  • The website data store, one per host
  • The WKWebView
  • Context and the toolbar items derived from it
  • The events stream
  • Session-scoped extensions
  • The entry route and any query

4.2 Lifecycle

  1. Created. SashView appears, or host.makeSession(route:) is called directly. Session-scoped extensions are instantiated.
  2. Loaded. The document finished loading. The shim has hydrated.
  3. Ready. The page called sash.ready(). Only now does the toolbar trust context and only now is an overlay update considered good.
  4. Ended. The view disappeared or the window closed. Extensions get a chance to flush. The web view is released.

Extensions receive each transition through session(_:didChange:). There is no suspended state in draft 1; a hidden window keeps running.

4.3 Focus and command routing

host.focused is the session whose window is key. Menu commands are routed to the focused session, and their enablement is read from that session's context. A session-scoped toolbar renders only for its own window.

4.4 Talking between sessions

sash.sessions.list() returns ids and routes. sash.sessions.send(id, name, payload) and sash.sessions.broadcast(name, payload) deliver sash:message events. Shared state is usually the better tool; messaging is for transient coordination such as "scroll to this item".

4.5 Opening more

The page cannot open a window by itself, and Sash ships no extension that lets it. If an app wants the page to ask, the developer writes a call such as sash.clocks.detach(city) whose handler does openWindow(value: Sash.Route("/clock/tokyo")) into the WindowGroup(for:) the app declared. That creates a new SashView and therefore a new session. Sheets and panels are the same pattern. What Sash provides is the plumbing: the Route value type, sessions that carry it, and host.makeSession(route:) for code that is not in SwiftUI.

4.6 Headless sessions

host.makeSession(route:, hidden: true) creates a session in an offscreen window. A WKWebView outside a window does not load, so Sash owns that window. Used by the test harness and by apps that want a JavaScript worker without UI.

6. Standard extensions three, all opt-in

Sash ships the extensions that every web app already assumes exist, and nothing else. The test for inclusion: does an ordinary page do this constantly, with no idea it is inside an app? Settings and local storage, network, clipboard. Everything else is something the app means to do, and an app that means to do something should say so in Swift.

NamespaceScopeCalls and behaviourNative backing
state corehost Not an extension, listed here because it is what most people reach for first. The store, the localStorage shim on the local scope, and the settings scope the Settings window binds to. See State and storage. UserDefaults, files, iCloud key-value
nethost fetch(request) proxied through URLSession, restricted to the hosts the Swift side listed at install. Streams bodies. Also installs a source-side allow-list so a plain page fetch("https://...") works for those hosts only. Nothing else in the process gives the page the network. URLSession
clipboardhost readText(), writeText(), readImage(), writeImage(). The Edit menu already covers cut, copy and paste inside the page; this is for programmatic use. NSPasteboard

Decided. Toolbar, menus, windows, files, notifications, haptics, keychain, dialogs, process, and a page-visible updater are not standard extensions. Each is a recipe in section 8 and a few lines of Swift in the app that wants it. The package stays small, the capability listing of any given app stays honest, and the work is done where the developer can see it.

The updater still exists. It is a host facility configured in Swift (see Updates) with no page namespace. An app that wants to show update status in the page writes a three-call extension over host.updater.

7. The extension protocol

public protocol SashExtension {
    static var namespace: String { get }
    static var scope: Sash.Scope { get }              // .host or .session
    static var requirements: [Sash.Requirement] { get }  // entitlements, usage strings

    func register(in registry: Sash.Registry)
    func session(_ session: Sash.Session, didChange state: Sash.SessionState)
}

public extension SashExtension {
    static var scope: Sash.Scope { .host }
    static var requirements: [Sash.Requirement] { [] }
    func session(_: Sash.Session, didChange _: Sash.SessionState) {}
}

What register(in:) can declare:

DeclarationAppears to the page asNotes
registry.call("name") { (args: A) async throws -> R } sash.<ns>.name(args) Codable in and out. Main actor by default; .detached option for work off the main thread.
registry.route(.get, "/api/x") { req in Response } fetch("/api/x") Bodies are AsyncSequence<Data>. Takes precedence over sources.
registry.stream("/api/ticks") { emitter in } new EventSource("/api/ticks") A route specialised for SSE. Ends when the session ends.
registry.script(source, at: .documentStart) JavaScript already running For polyfills and shims. Main frame only.
registry.event("name") Documented in capabilities Declares events the extension emits so the JS table can type them.
registry.command("id", title:, key:) sash:command Registers a native menu command the page may claim in context.

A session-scoped extension is instantiated by the registry with the session injected, so it can reach the window and the web view. A host-scoped extension receives the session as a parameter in its handlers. Extensions may depend on other extensions by namespace; the registry resolves order and fails at startup if a dependency is missing.

The whole haptics extension, for scale:

struct Haptics: SashExtension {
    static let namespace = "haptics"
    enum Pattern: String, Decodable { case alignment, levelChange, generic }
    struct Perform: Decodable { var pattern: Pattern }

    func register(in r: Sash.Registry) {
        r.call("perform") { (a: Perform) in
            NSHapticFeedbackManager.defaultPerformer
                .perform(a.pattern.native, performanceTime: .now)
        }
    }
}

8. Writing your own the intended path

The pattern is always the same. The page describes what it wants in an object. A Swift extension receives the object and does the native work. If the native side will need to talk back later, the extension hands the page a handle and reports through an event when something happens. The page never learns how the work was done.

8.1 Save something

The page does not get a filesystem. It gets a call that means "here is a document".

struct Documents: SashExtension {
    static let namespace = "documents"
    struct Save: Decodable { var id: String; var title: String; var body: String }

    func register(in r: Sash.Registry) {
        r.call("save") { (doc: Save) async throws -> String in
            let url = try await DocumentStore.shared.write(doc)   // panel, container, iCloud: your call
            return url.lastPathComponent
        }
        r.call("list") { () async throws -> [DocumentSummary] in
            try await DocumentStore.shared.list()
        }
    }
}
const name = await sash.documents.save({ id, title, body })

8.2 Notify, and hear back

The page sends an object and gets back an endpoint. When the user acts on the notification, Swift calls that endpoint, which reaches the page as an event. The page decides what happens; Swift decided how it was shown.

struct Alerts: SashExtension {
    static let namespace = "alerts"
    struct Post: Decodable { var title: String; var body: String; var actions: [String] }
    struct Posted: Encodable { var id: String; var endpoint: String }

    func register(in r: Sash.Registry) {
        r.event("alerts:activated")
        r.call("post") { (p: Post, session: Sash.Session) async throws -> Posted in
            let id = UUID().uuidString
            let content = UNMutableNotificationContent()
            content.title = p.title; content.body = p.body
            try await UNUserNotificationCenter.current().add(
                UNNotificationRequest(identifier: id, content: content, trigger: nil))
            NotificationRouter.shared.onActivate(id) { action in
                session.emit("alerts:activated", ["id": id, "action": action])
            }
            return Posted(id: id, endpoint: "/_ext/alerts/\(id)")
        }
        r.route(.post, "/_ext/alerts/:id") { req in        // the same endpoint, reachable by fetch
            NotificationRouter.shared.activate(req.params["id"]!, action: "opened")
            return .ok
        }
    }
}
const { id } = await sash.alerts.post({ title: "Tokyo", body: "It is 9 am", actions: ["Open"] })
sash.on("alerts:activated", ({ id, action }) => router.go(`/clock/${id}`))

The endpoint in the reply is optional. It exists so a page that prefers plain HTTP, or a second session, can trigger the same activation without the event bus.

8.3 A toolbar item

No toolbar extension. The page reports context; Swift renders whatever toolbar it likes from it and sends taps back as commands. The page's side is one line.

sash.context.set({ title: city.name, commands: ["clock.add", "clock.remove"] })
struct ClockToolbar: ToolbarContent {
    let host: Sash.Host
    var context: Context? { host.focused?.context }
    var body: some ToolbarContent {
        ToolbarItem(placement: .primaryAction) {
            Button("Add", systemImage: "plus") { host.send("clock.add") }
                .disabled(!(context?.handles("clock.add") ?? false))
        }
    }
}

8.4 A menu

Same mechanism. CommandMenu in Swift, enablement from the focused session's context, session.send("clock.add") delivering sash:command. Sash registers the Edit, Window and Help menus; the rest is the app's.

8.5 Anything with hardware or permissions

Haptics, location, camera, speech: a call, a Codable argument, the framework call in the handler, and a requirements entry naming the usage string so Sash fails at startup if the Info.plist lacks it. Haptics is nine lines; see section 7.

8.6 A companion for a command-line tool

An extension that owns a Process, allow-lists the executable, streams stdout as an SSE route, and exposes run(args). This is what Vaelth.app's doctor and repair become. It is a recipe and not a standard extension because the allow-list and the elevation policy are the whole design, and they are the app's.

9. Sources

A source answers a request for a path with a response or passes. The host holds an ordered chain and route handlers are consulted before it.

SourceServesNotes
.bundle(Bundle, subdirectory:)Files embedded in the app or package.Correct MIME types, ETag from file hash, index fallback for SPA routers.
.overlay(directory)An updated web layer.Layered before the bundle. Switched atomically. See Updates.
.socket(path)HTTP over a unix socket.What Vaelth.app does. Streams. Health reported to the host.
.remote(URL, allow:)An HTTPS origin.Optional cache. For mixed online-and-local apps.
.dev(URL)A dev server such as Vite.Live reload passes through. Debug builds only.

10. State and storage

  • Scopes. Named partitions. local backs the shim. settings backs the Settings window. Developers add their own. Each scope names its persistence and its visibility.
  • Persistence. .memory, .userDefaults(suite), .file(url) as JSON with atomic writes, .ubiquitous for iCloud key-value. Keychain is deliberately not a store backend; secrets go through the keychain extension.
  • Visibility. A scope is page-visible or Swift-only. Swift-only scopes still get observation; they just never cross the bridge.
  • Consistency. Last write wins. Every write is stamped with session id and sequence so a page can ignore its own echo. There is no transaction API in draft 1.
  • SwiftUI. @Bindable var s = host.store.scope("settings") gives bindings that the page sees change through sash:state.
  • WebKit storage. Cookies, IndexedDB, and Cache API stay in a per-host WKWebsiteDataStore(forIdentifier:). Sash does not shim them. Service workers do not run on custom schemes, and Sash does not try to change that.

11. Updates

ChannelMechanismGuards
App bundle Appcast JSON, download, verify, in-place swap, relaunch. SHA-256 must match. Code signature must validate and match the running bundle's team. Swapping ourselves bypasses Gatekeeper, so the updater does Gatekeeper's job.
Web layer Manifest of files with hashes, signed. Downloaded into an overlay directory; switched in on next load or on request. Ed25519 signature verified with a key embedded in the app. Manifest declares requires.api; the host refuses a manifest outside its range. If no session reaches ready within a timeout after switching, the overlay is marked bad and the previous layer is restored.

Two artifacts, two versions, two CDN paths. A release may move either or both. The overlay keeps the previous layer for rollback and prunes older ones.

Both channels are configured on the host in Swift: Sash.Host(web:, updates: .init(app: .appcast(url), web: .manifest(url, publicKey: key))). There is no page namespace. Swift observes host.updater.status and shows it however the app likes; an app that wants the page to show it writes a three-call extension over that object.

12. Security

  • The page has an origin nothing else can share and no route to the network except through declared sources or the net extension.
  • Navigation policy denies anything outside sash://app. External links go through sash.open, which opens the default browser.
  • Calls, routes, and page-visible store scopes are the entire capability surface. The capability listing is the permission story, and it can be shown in About.
  • Extensions marked sensitive, such as process and files with persisted bookmarks, are labelled as such in the listing. Sash does not gate them at runtime; the developer chose to install them.
  • Extension requirements are checked at startup against the bundle's entitlements and Info.plist, and missing ones fail loudly.
  • Argument decoding is strict. An unknown field is invalid-args, not ignored.

13. Testing

  • SashTesting boots a host with a headless session and awaits ready, against the real bundle or a fixture directory.
  • Extensions can be exercised without WebKit by calling the registry directly with JSON, which is how most extension tests should be written.
  • JavaScript-side assertions run through session.evaluate with a timeout and structured results.
  • The .dev source plus an optional localhost mirror of the route table lets the page be opened in Safari with real developer tools during development.

14. Package layout and platform

  • Platform. macOS 15 or later, Swift 6 language mode. The core avoids AppKit where it can so an iOS port is a matter of a second view type, not a rewrite.

15. Decisions log

DecisionWhy
The JavaScript global is sash.Distinctive, short, no collision with common page code.
Scheme sash://app/, framework paths under /_sash/.A fixed authority keeps location.host stable; a reserved prefix keeps the developer's paths free.
The view is a session; the host is the object.Full SwiftUI control and any number of web views fall out of it.
Storage is a host property, not an extension.The shim must work before extensions run.
Menus and windows are Swift's; the page asks through extensions.The page never gains chrome the developer did not grant.
Routes win over sources.So /api can be Swift while / is the bundle without configuration.
Calls are generated, never hand-written.The registry is the single source of truth, and has() is always right.
No runtime permission prompts from Sash.Installing an extension is the grant. The OS still prompts where it prompts.
Three standard extensions: state, net, clipboard.They are what an ordinary page assumes exists. Everything else is intent, and intent belongs in the app's Swift where its policy is visible.
The page describes, Swift does, a handle comes back.The recipe shape for everything from saving to notifications. It keeps the page portable and the capability listing honest.
No toolbar, menu or window extension.Context plus commands already carries what those need, and the rendering is SwiftUI the developer would rather own.
The updater has no page namespace.It is a host facility. Showing it in the page is a three-call extension.
macOS 15 minimum, no dependencies.One OS generation to test; the exception bridge is small enough to embed.
The class is SashHost, spelled Sash.Host.Foundation exports a Host already, and every app imports Foundation.
session.send and host.send, not context.send.Context is a value; the session is what can talk to the page.
Request bodies are buffered; response bodies stream.WebKit hands the whole request body over at start. Streaming responses is what SSE needs.
Strict rejection of unknown call fields is deferred.JSONDecoder cannot do it without a tracking decoder. Missing and mistyped fields are still invalid-args.
Persistence in milestone 1: memory and UserDefaults.File and iCloud backends follow when an app needs them.
Rule-list regexes avoid alternation.WebKit's content-blocker dialect rejected (/|$); a resolved URL always has a path, so / closes the host.

16. Open questions

  • Whether route handlers should use a small server type of our own or adopt an existing request-response vocabulary. Leaning own, kept tiny.
  • Whether the recipes should ship as a third SwiftPM product after all, once a few apps have shown which ones stabilise.
  • How many overlay versions to keep and whether the page may pin one.
  • Whether a session may be suspended when its window is hidden for a long time, and what the page sees if so.
  • Whether to expose WKWebView directly to advanced users through an escape hatch on the session. Leaning yes, documented as unsupported.
