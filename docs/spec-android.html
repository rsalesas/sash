Sash for Android

Specification, draft 1. The same contract as Sash for macOS, hosted by a Kotlin library in a Jetpack Compose app: your Compose, your activities, your top bar; the web app in a view; extensions as the only door between them. One web folder ships in both apps unchanged. Where this document repeats the macOS one it says so; where Android differs it says why.

0. Reader's map

What the page sees is identical. What the native side does to make that true is different in five places, and each is a consequence of one fact about Android's WebView. The full table with verification status is in the appendix.

Fact about WebViewConsequenceSection
Custom schemes are opaque origins: no fetch, no EventSource, no stable location.host. The page is served at https://app.sash.invalid/ from shouldInterceptRequest. Nothing else changes. 3.1
Interception never sees a request body. The runtime tunnels same-origin fetch requests that carry a body through the call bridge and streams the reply back over interception. Page code is unchanged. 3.7
Interception never sees WebSockets, service workers, or redirect hops, and there are no content rule lists. Network policy is a 403 from interception plus a Content-Security-Policy header on every HTML document. macOS sets no CSP; this one is permissive except for network. 12
An Activity is recreated on rotation. The host owns sessions, not the view. SashView re-attaches an existing session's WebView; a session ends only when its view leaves for good. 4.2
There is no APK swap an app may do to itself. The web channel is identical and consumes the same signed manifests. The app channel does not exist; the store is the app updater. 11

1. Purpose and scope shared

Sash makes a web app a good citizen of Android without pretending to be a cross-platform framework. The developer writes a normal Compose app and a normal single-page web app, the same one that ships in the macOS app. Sash supplies the view that hosts the page, the interceptor that serves it, the store that both sides share, and the registry through which Kotlin grants the page capabilities one at a time.

  • In scope. Everything the macOS package does that has an Android meaning: hosting, serving, streaming, state, the call bridge, context reporting, many simultaneous web views, the three standard extensions, the web update channel, a test harness. Two things macOS never had to think about: sessions that survive configuration changes, and the system back gesture.
  • Out of scope. A JavaScript UI framework. An APK updater. Views-based chrome beyond the one SashWebView class. Anything that makes the page reach the operating system without a Kotlin declaration.

Design rule. The page talks HTTP and a small JavaScript object. Kotlin decides who answers. Nothing the page can reach exists unless Kotlin declared it.

2. Concepts same with caveat

TermWhat it isCardinality
Host SashHost, owning the registry, the store, the sources, and the list of live sessions. Created once, in Application.onCreate or a lazy singleton, never in an Activity: activities die on rotation and the host must not. One per app, more if you want isolated worlds.
Session One WebView plus its context, its events stream, and its per-session extensions. Has an id, an entry route, and a key that lets a recreated Activity find it again. As many as you like. One per SashView key.
SashView The composable. Wraps AndroidView, finds or makes the session for its key, attaches the web view on enter, detaches or ends it on leave. Takes a host, an optional route, an optional key. SashWebView, the View underneath, is public for apps that are not Compose. Anywhere a composable goes.
Source Answers requests for the web layer's files: assets, directory, overlay, socket, remote, dev. One chain per host.
Extension A Kotlin type that declares calls, routes, streams, and scripts under a namespace, and hooks session lifecycle. Installed per host; instantiated per host or per session by its scope.
Store The shared key-value state, JSON values, scoped by name, with pluggable persistence. Backs sash.state, the localStorage shim, and the settings screen. One per host.
Context What a session's page is showing: title, subtitle, view id, selection, dirty, commands it can handle. A Compose State. One per session.

The Settings window becomes a destination; the toolbar becomes TopAppBar actions; the CommandMenu becomes the overflow menu plus hardware-keyboard shortcuts. The page does not know any of this happened.

3. The web contract shared

Everything the page can do is one of four things: fetch a URL, open an events stream, call a declared function, or read and write shared state. The global is window.sash. Sections 3.2 through 3.6 are the macOS text; only 3.1 and 3.7 carry Android facts.

3.1 Origin and paths same with caveat

  • The page is served at https://app.sash.invalid/. Every request to that origin is answered in-process by WebViewClient.shouldInterceptRequest; none reaches the network. The host is under .invalid, reserved by RFC 2606, so a request that ever escaped interception would get NXDOMAIN rather than a real server. A single-label host such as https://app/ was rejected because DNS search suffixes on managed networks can resolve it.
  • Why not sash://app/: Chromium treats a custom scheme as an opaque origin. Relative URLs do not resolve, fetch and EventSource fail, and location.host is empty. An https origin gives the page a secure context, working relative URLs, and storage keyed to a stable origin.
  • location.pathname is the entry route on both platforms. location.protocol and location.host are not the same on both (sash:/app on macOS). The contract promised only that the host is stable. A page that needs its own origin as a string reads sash.origin (section 17) and never hardcodes either.
  • /_sash/* is reserved for the framework. Everything else belongs to the developer's sources and routes. Route handlers registered from Kotlin take precedence over the source chain.
PathPurpose
/_sash/eventsThe per-session Server-Sent Events stream. Named events; JSON data.
/_sash/stateBulk read of the store scopes the page may see.

3.2 Calls

A message is { id, ns, name, args }; the reply is { ok, value } or { ok: false, error: { code, message, data } }. The generated table turns that into await sash.haptics.perform({ pattern: "levelChange" }). Arguments and results are JSON; Kotlin handlers see @Serializable types.

Error codes are fixed: capability-missing, invalid-args, denied, unavailable, failed. A call into an uninstalled namespace rejects with capability-missing; it is never undefined.

On Android the reply also carries the id, because the transport is a per-frame channel rather than a per-message promise (4.8). The runtime correlates; the page never sees the difference.

3.3 Events

The page opens new EventSource("/_sash/events"), or uses sash.on(name, fn) which does the same. Kotlin pushes with session.emit(name, payload) for one session or host.broadcast(name, payload) for all. Framework events are prefixed sash:; developers own the rest of the namespace.

EventWhen
sash:helloThe stream connected. Carries storeSeq, so a page that missed changes resyncs.
sash:stateA store key changed, from Kotlin or from another session. Carries scope, key, value, origin.
sash:appearanceDark mode, accent colour, locale, hour cycle, reduced motion or contrast changed. Carries the whole platform object.
sash:focusThis session's window gained or lost focus.
sash:commandA top-bar, menu or keyboard command the page declared it handles.
sash:capabilitiesAn extension was installed after load.
sash:messageAnother session sent this one a message.
sash:web-updatedA new web layer was installed and probed. Not pre-attached; subscribe with sash.on.
sash:terminateReserved. Emitted by neither platform today.

3.4 State

sash.state.get(scope, key), set, remove, keys, all, watch, flush. Synchronous reads against a local mirror hydrated at document start; writes are applied locally and forwarded in one microtask batch, so the page never waits. localStorage is shimmed onto the local scope. Settings live in the settings scope. Which scopes a page may see is declared on the host.

3.5 Context

sash.context.set({ title, subtitle, view, selection, dirty, commands }). Partial updates merge. Kotlin reads session.context as Compose state. The commands array names the sash:command identifiers this view will handle, which is what enables the matching top-bar actions and menu items.

3.6 Session identity

sash.session exposes { id, route, isFocused }. The entry route is also the page's location.pathname, so an SPA router needs nothing special.

3.7 Requests with bodies same with caveat

shouldInterceptRequest is called for a POST, but WebResourceRequest has no body accessor. The runtime closes the gap so that fetch("/api/x", { method: "POST", body }) against a Kotlin route works exactly as it does on macOS:

  1. At boot the runtime learns from the snapshot that bodies are tunnelled. It wraps window.fetch. Same-origin requests without a body pass straight through to interception. Same-origin requests with a body are serialised (text as text, binary as an ArrayBuffer message where the WebView supports it, otherwise base64, FormData as hand-built multipart) and posted over the call bridge.
  2. Kotlin dispatches the request through the same router and source chain as any other, parks the Response under a one-shot ticket with a 30-second life, and replies with the ticket.
  3. The runtime returns fetch("/_sash/r/<ticket>"), which interception answers by replaying the parked status, headers and body, streamed, with Cache-Control: no-store. The page receives a genuine Response with a readable body stream, so SSE over POST and /_sash/net/fetch both work.

Cross-origin requests are not wrapped; the network policy decides those. Not covered, and said so: navigator.sendBeacon, <form method="post"> as a main-frame navigation, and XMLHttpRequest with a body. A page that uses those against a Kotlin route is not portable, and the checklist in section 17 says so. Bodies of a ReadableStream reject with invalid-args.

Decided. Tunnel through the bridge rather than run a loopback HTTP server. A server on 127.0.0.1 is a second origin, so every request is cross-origin to the page; its port is not stable so it cannot be the origin; and any app on the device can connect to it, so every request would need a token. Restricting routes to GET was rejected because it breaks the published contract.

4. Sessions and many web views same with caveat

A host may have any number of live sessions. Two activities showing the same page, a main screen and a detail screen, a bottom sheet with a form, a hidden worker session running background JavaScript: all sessions, all equal.

4.1 What is shared and what is not

Shared across sessionsPer session
  • The store, so localStorage in one screen is visible in another after sash:state
  • The source chain and route table
  • Host-scoped extensions
  • The interceptor, the network policy and its CSP
  • WebView storage (cookies, IndexedDB, Cache API), which Android keys per app data directory
  • One ServiceWorkerClient that refuses everything
  • The WebView, and the __sashBridge listener on it
  • Context and the top-bar actions derived from it
  • The events stream
  • Session-scoped extensions
  • The entry route, any query, and the key

4.2 Lifecycle, and surviving rotation differs

On macOS a SashView owns its session: appear creates, disappear ends. On Android the Activity that hosts a composable is destroyed and recreated on rotation, on a locale change, on a dark-mode switch. If the session died with it, every one of those would reload the page and lose its state. So the host owns sessions, and the view borrows them.

  1. Created. SashView(host, route, key) enters composition and finds no session for key, or host.makeSession(route:, key:) is called directly. The WebView is built on a MutableContextWrapper around the application context. Session-scoped extensions are instantiated.
  2. Attached. The view swaps the wrapper's base context to the Activity, so dialogs, autofill and theme resolve against a real window, and adds the WebView to its AndroidView. A session may be attached to one view at a time.
  3. Loaded. The document finished loading. The runtime has hydrated.
  4. Ready. The page called sash.ready(). Only now does the top bar trust context and only now is an overlay update considered good.
  5. Detached. The composable left because the Activity is changing configuration (activity.isChangingConfigurations). The WebView is removed from its parent and its base context reset to the application. The page keeps running. The recreated Activity's SashView, with the same key from rememberSaveable, attaches it again.
  6. Ended. The composable left for any other reason, or session.end() was called. Extensions get a chance to flush. The WebView is destroyed.

Extensions receive each transition through session(session, state), with the same four states as macOS; attached and detached are not states the page or extensions observe. Process death ends everything: the key survives in saved instance state, the store is on disk, and a fresh session loads the same route with the same state. There is no WebView.saveState; the page is the source of truth for its own view state and the store for everything else.

If the render process dies (onRenderProcessGone), the session replaces its WebView under the same id and reloads. SashView recomposes around the new instance. This is the macOS "web content process terminated; reloading" case.

4.3 Focus and command routing

host.focused is the session whose WebView last reported onWindowFocusChanged(true). Commands from host.send are routed to it, and their enablement is read from that session's context. In multi-window mode two activities can be visible; only one has window focus, which is the right one to receive a keyboard shortcut.

4.4 Talking between sessions

sash.sessions.list(), sash.sessions.send(id, name, payload) and sash.sessions.broadcast(name, payload), delivering sash:message. Shared state is usually the better tool.

4.5 Opening more

The page cannot open a screen by itself. If an app wants the page to ask, the developer writes a call such as sash.clocks.detach(city) whose handler starts an Activity, or navigates a NavHost, carrying a Route. Route is Parcelable so it rides in an Intent extra or a saved-state handle. The destination renders SashView(host, route), which is a new session. Bottom sheets and dialogs are the same pattern.

4.6 Headless sessions

host.makeSession(route, hidden = true) creates a session whose WebView is never attached to a window. Unlike WebKit, Chromium loads and runs scripts in an unattached WebView: its web contents are merely hidden. document.visibilityState is "hidden", timers are aligned to one second, and requestAnimationFrame does not fire. Used by the update probe and by apps that want a JavaScript worker without UI. Because of it, sash.ready() must be called from the load path and never from an animation frame; the checklist in section 17 makes this a rule on both platforms.

4.7 No browser showing through

The view is an app's interface, not a document the user browses. Android's WebView starts closer to that than WebKit does: it has no context menu on links, no reload the user can reach, no back button of its own. What remains is taken out or pinned down:

  • Zoom. setSupportZoom(false), setBuiltInZoomControls(false), setDisplayZoomControls(false). Pinch does nothing.
  • Text size. Left at the default, which follows the system font scale. macOS has no equivalent setting; this is an accessibility control and Sash does not override it. A page that must not reflow can set textZoom through the escape hatch, and is told not to.
  • Dark mode. WebSettingsCompat.setAlgorithmicDarkeningAllowed(false). The page owns its appearance through data-sash-appearance; Chromium must not repaint it. The app should use a DayNight theme so prefers-color-scheme agrees with sash.platform.appearance.
  • Selection. The floating action mode on selected text is trimmed to Copy, Select all and Paste; Share and Web search are a browser's. The page still receives contextmenu on long-press and may draw its own menu.
  • Overscroll. OVER_SCROLL_NEVER by default, exposed as a parameter. The glow says "document".
  • Reload. Nothing to remove. Session.reload() and the updater still reload; reloading is the app's decision.
  • Inspector. Debuggable builds are inspectable from chrome://inspect automatically; release builds are not.
  • Back. Off by default. SashView(handleSystemBack = true) installs a BackHandler that calls goBack() while the page has history. Most Sash pages are single documents with a client-side router, and whether back means "close the sheet", "previous route" or "leave the app" is the app's to decide, so it is a parameter and not a default.
  • Files. allowFileAccess and allowContentAccess are off. Mixed content is never allowed.

4.8 The plumbing under a session differs

The page's contract is the same. What carries it:

PieceAndroidNotes
Calls WebViewCompat.addWebMessageListener(webView, "__sashBridge", setOf("https://app.sash.invalid"), listener) The injected object is named __sashBridge, never sash: the listener defines a global of that name, and sash is ours. Replies go back through the JavaScriptReplyProxy, which is a per-frame channel, so the runtime matches them by id. Both sides run on the main thread.
Boot snapshot WebViewCompat.addDocumentStartJavaScript once, containing a guard, a synchronous read of __sashBoot.snapshot(), the runtime, and extension scripts. __sashBoot is a one-method addJavascriptInterface object. macOS re-installs the user script before every main-frame navigation to refresh the snapshot; Android reads it fresh each time the script runs, which also covers reload(). The read happens on the WebView's JavaBridge thread, so the snapshot comes from a lock-protected mirror and never touches the main thread. Start scripts run in every frame that matches the origin rule, so the script begins with if (window !== window.top) return; for parity with forMainFrameOnly.
Document-end scripts Wrapped in DOMContentLoaded inside the start script. There is no document-end injection API.
Serving shouldInterceptRequest returning a WebResourceResponse Called on a pool of background threads that may block, concurrently. The response head is produced by hopping to the main thread and waiting, with a time box that turns a stuck handler into a 504 instead of a pinned thread. Bodies are an InputStream fed from a coroutine.
Streaming A queue-backed InputStream; null is end of stream. Chromium reads the stream on a background thread in small chunks and forwards each read before end of stream, so SSE works. Two facts shape it: Chromium withholds the response head until the first read completes, which is why the stream begins with a : ok comment on both platforms; and Chromium may not close the stream when the page stops listening, so every emitter sends a heartbeat comment every 15 seconds and a parked read wakes, fails, and releases its thread. PipedInputStream is not used because its liveness check is tied to a writer thread, which coroutines do not keep.
Navigation shouldOverrideUrlLoading Allows the Sash origin. http, https and mailto go to Intent.ACTION_VIEW; anything else is refused and logged. Main-frame requests that bypass this callback still meet the interceptor's policy.
target="_blank" setSupportMultipleWindows(true) and onCreateWindow Returns a throwaway WebView whose client opens the URL externally and destroys itself. With multiple windows off, Chromium would navigate the page instead, which is the naive-wrapper bug.
Evaluate evaluateJavascript("(async () => { … })()"), result parsed as JSON. session.evaluate(body) keeps function-body semantics: return and await allowed.

7. The extension protocol shared

interface SashExtension {
    val namespace: String
    val scope: ExtensionScope get() = ExtensionScope.Host       // or Session
    val requirements: List<Requirement> get() = emptyList()     // permissions, features
    val dependencies: List<String> get() = emptyList()          // namespaces installed first

    fun register(registry: Registry)
    fun session(session: Session, state: SessionState) {}
}

sealed interface Requirement {
    data class Permission(val name: String) : Requirement    // must be declared in the manifest
    data class Feature(val name: String) : Requirement       // PackageManager.hasSystemFeature
}

What register can declare:

DeclarationAppears to the page asNotes
registry.call<A, R>("name") { args -> R } sash.<ns>.name(args) @Serializable in and out, decoded strictly: an unknown field is invalid-args. Overloads take (args, session), (session), or nothing. Runs on the main thread; detachedCall runs on Dispatchers.Default.
registry.route(GET, "/api/x") { req -> Response } fetch("/api/x") Bodies are Flow<ByteArray>. Takes precedence over sources. Request bodies arrive complete, through the tunnel when the page sent one.
registry.stream("/api/ticks") { emitter, req -> } new EventSource("/api/ticks") A route specialised for SSE. Ends when the session ends.
registry.script(source, at = DocumentStart) JavaScript already running Main frame only. DocumentEnd is emulated (4.8).
registry.event("name") Documented in capabilities Declares events the extension emits.
registry.command("id", title = , key = ) sash:command Registers a command the page may claim in context; key is a hardware-keyboard shortcut the app's key handler may honour.

Requirements are checked at install, before any page loads, and a missing one throws. A missing permission surfaces where the developer is looking, not at first call in the field.

The whole haptics extension, for scale:

class Haptics : SashExtension {
    override val namespace = "haptics"
    @Serializable enum class Pattern { alignment, levelChange, generic }
    @Serializable data class Perform(val pattern: Pattern)

    override fun register(registry: Registry) {
        registry.call<Perform, Unit>("perform") { a, session ->
            session.webView.performHapticFeedback(a.pattern.constant)
        }
    }
}

8. Writing your own the intended path shared

The pattern is the macOS one. The page describes what it wants in an object. A Kotlin extension receives the object and does the native work. If the native side will need to talk back later, the extension hands the page a handle and reports through an event. The page never learns how the work was done, which is exactly why the same page runs on both platforms.

8.1 Save something

class Documents(private val app: Application) : SashExtension {
    override val namespace = "documents"
    @Serializable data class Save(val id: String, val title: String, val body: String)

    override fun register(registry: Registry) {
        registry.call<Save, String>("save") { doc ->
            DocumentStore(app).write(doc)        // app files, MediaStore, or ACTION_CREATE_DOCUMENT: your call
        }
        registry.call<Unit, List<DocumentSummary>>("list") { DocumentStore(app).list() }
    }
}

8.2 Notify, and hear back

class Alerts(private val app: Application) : SashExtension {
    override val namespace = "alerts"
    @Serializable data class Post(val title: String, val body: String, val actions: List<String>)
    @Serializable data class Posted(val id: String, val endpoint: String)

    override fun register(registry: Registry) {
        registry.event("alerts:activated")
        registry.call<Post, Posted>("post") { p, session ->
            val id = UUID.randomUUID().toString()
            val tap = PendingIntent.getBroadcast(app, 0, AlertReceiver.intent(app, id), FLAG_IMMUTABLE)
            NotificationManagerCompat.from(app).notify(id.hashCode(),
                NotificationCompat.Builder(app, CHANNEL).setContentTitle(p.title).setContentText(p.body)
                    .setSmallIcon(R.drawable.ic_alert).setContentIntent(tap).build())
            AlertRouter.onActivate(id) { action -> session.emit("alerts:activated", mapOf("id" to id, "action" to action)) }
            Posted(id, "/_ext/alerts/$id")
        }
        registry.route(POST, "/_ext/alerts/:id") { req ->
            AlertRouter.activate(req.params.getValue("id"), "opened"); Response.ok
        }
    }
}

POST_NOTIFICATIONS is a runtime permission on Android 13 and later. The handler requests it the first time through the attached Activity; the extension's requirements names it so the manifest cannot forget it.

8.3 A top-bar action

No toolbar extension. The page reports context; Compose renders whatever it likes from it and sends taps back as commands. The page's side is one line, and it is the same line as on macOS.

    }
    IconButton(onClick = onSettings) { Icon(Icons.Default.Settings, contentDescription = "Settings") }
}

8.4 A menu and a shortcut

Same mechanism. An overflow DropdownMenu whose items are enabled from the focused session's context, and a Modifier.onPreviewKeyEvent on the screen that turns Ctrl+N from a hardware keyboard into host.send("clock.add"). On macOS the same command is ⌘N; the page shows whichever hint fits by reading sash.platform.family.

8.5 Anything with hardware or permissions

Haptics, location, camera, speech: a call, a serializable argument, the framework call in the handler, and a requirements entry naming the permission so Sash fails at install if the manifest lacks it. Runtime permission prompts happen inside the handler, through the attached Activity, and a denial is denied.

8.6 A companion process

An extension that owns a bound Service, exposes run(args), and streams its output as an SSE route. Foreground-service rules and the process-lifetime policy are the whole design, and they are the app's, which is why this is a recipe.

9. Sources same with caveat

A source answers a request for a path with a response or passes. The host holds an ordered chain and route handlers are consulted before it. The rules for static files are the macOS rules: correct MIME types from the same table, an ETag from the first twelve bytes of the file's SHA-256, 304 on If-None-Match, index.html for a directory, the root index.html for a miss that does not look like an asset or that accepts HTML, and any .. segment refused rather than normalised.

10. State and storage same with caveat

  • Scopes. Named partitions. local backs the shim. settings backs the settings screen. Developers add their own. Each scope names its persistence and its visibility.
  • Persistence. Memory; Preferences(name), which is SharedPreferences with one JSON string per scope under the key sash.store.<scope>; and File(directory), one JSON file per scope written through AtomicFile. SharedPreferences rather than DataStore because the store is synchronous by contract: the boot snapshot is read on the WebView's bridge thread at document start, and an asynchronous backend would put a blocking wait there. ubiquitous does not exist on Android; there is no cross-device key-value store. Auto Backup restores a device, it does not sync two, and the spec says so rather than pretend. Keystore is deliberately not a store backend.
  • Visibility. A scope is page-visible or Kotlin-only. The page's writes to a Kotlin-only scope are refused and logged.
  • Consistency. Last write wins. Every write is stamped with session id and sequence so a page can ignore its own echo. No transaction API.
  • Compose. scope.state("showSeconds", default = true) returns a MutableState<Boolean> that reads and writes the store, so a Switch bound to it changes the clocks while the settings screen is still open, through sash:state. This is Scope.binding under a Compose name.
  • WebView storage. Cookies, IndexedDB, and Cache API belong to the origin and live in the app's data directory. Sash does not shim them. Service workers are refused by a ServiceWorkerClient that answers every request with 403, so a page cannot register one by accident and find that it works on one platform and not the other.

One release of the web layer serves both platforms: the manifest has no platform field, and the files are the same. An app that ships a platform-specific layer uses two manifest URLs.

Ed25519 verification is a vendored implementation of RFC 8032 with no dependency, tested against the RFC vectors and against manifests signed by the release tool. The platform's Signature.getInstance("Ed25519") exists only from API 33, and two code paths would be two behaviours; debug builds on 33 and later cross-check the vendored result against the platform and log any disagreement.

The channel is configured on the host: SashHost(app, web = , updates = UpdateConfiguration(web = WebChannel(manifestURL = , publicKey = ))). There is no page namespace. Kotlin observes host.updater.status as Compose state, calls check() and apply(), and shows it however the app likes. relaunch() does not exist; a new layer is served to the next document, and updater.reloadSessions() reloads visible ones now. The page hears sash:web-updated when a new layer is in.

12. Security same with caveat

  • The page has an origin nothing else can share, served by nothing but the interceptor, and no route to the network except through declared sources or the net extension.
  • Navigation policy denies anything outside https://app.sash.invalid. External links go through sash.open.
  • Calls, routes, and page-visible store scopes are the entire capability surface. The capability listing is the permission story.
  • Extension requirements are checked at install against the manifest, and missing ones throw.
  • Argument decoding is strict. An unknown field is invalid-args, not ignored.

12.1 Network policy without rule lists

WebKit compiles the allow list into a content rule list that blocks every http, https, ws and wss request the list does not permit, before the request exists. Android has no such thing, and shouldInterceptRequest cannot see three kinds of traffic: WebSocket handshakes, service-worker fetches, and the later hops of a redirect. So the policy has two layers, and both come from the one allow list:

  1. The interceptor. A request to the Sash origin is dispatched. A request to an http or https host on the allow list returns null, and Chromium fetches it. Anything else receives a synthesised 403 with an empty body and no CORS headers, so a cross-origin fetch fails with a network error exactly as it does under the WebKit blocker, and an <img> or <script> fires error.
  2. The header. Every HTML document the interceptor serves carries Content-Security-Policy: default-src 'self' data: blob: 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' https://h1 wss://h1 https://*.h2 wss://*.h2 …, one https and wss pair per allow-list pattern. default-src rather than connect-src alone, so a permitted host that redirects to a forbidden one is stopped for every resource type. Everything that is not network is allowed, because macOS sets no CSP and the page must not behave differently. Without the net extension the list is empty and the header says 'self' and nothing else.

Service workers are refused outright by the host's ServiceWorkerClient. Mixed content is MIXED_CONTENT_NEVER_ALLOW. Safe Browsing stays on; the origin host is allow-listed through WebViewCompat.setSafeBrowsingAllowlist so intercepted URLs are not checked against a service that will never have seen them.

Verified by mechanism, not end to end. Chromium delivers an intercepted response's headers as the real response head, which is what CSP enforcement reads. That the header on an intercepted document is honoured has not been demonstrated in a Sash build yet. It is the milestone-1 spike, the way the localStorage shim was on macOS.

13. Testing same with caveat

  • sash-testing boots a host with a hidden session and awaits ready, against the real assets or a fixture directory, in an instrumented test. Harness.boot(host), Harness.waitUntil { }, session.evaluate(body). A real WebView needs a device or emulator; Robolectric does not execute WebView scripts, and the harness says so rather than skip silently.
  • Extensions can be exercised without a WebView by calling the registry directly with JSON, in ordinary JVM unit tests, which is how most extension tests should be written.
  • The dev source over adb reverse plus chrome://inspect gives the page real developer tools during development.
  • The example tests are the macOS ones, translated: Calculator computes from synthesised key events; World Clock persists a city across two hosts on the same preferences file, flips showSeconds from Kotlin and sees one colon, copies through the clipboard, and reports the same hourCycle the host does.

16. Open questions

  • The maximum size of a postMessage through the message listener is undocumented. The tunnel should route bodies above a megabyte through an upload ticket instead; the threshold needs measuring.
  • Whether the service-worker script fetch itself passes through ServiceWorkerClient, or only the fetches a registered worker makes. If not, worker-src 'self' in the CSP is the second lock.
  • The high-contrast signal below API 34 is a hidden setting read by name. If it proves unreliable, report false and say so.
  • sendBeacon and form-navigation POSTs to Kotlin routes. Probably never; the checklist forbids them.
  • Whether macOS should also expose sash.origin now, or only when the first page needs it.
  • Whether sash.open should offer Custom Tabs. Leaning no: the page asked to leave.
  • Whether a detached session should be suspended after a long time off screen, and what the page sees if so. Same question as on macOS.
  • Whether to expose the WebView through session.webView as macOS does. Leaning yes, documented as unsupported.

17. One page, two platforms

The contract was designed so that the page never learns how the work was done. Two platforms test that claim, and it holds with three additions to the runtime and a short list of habits for the page. The additions are additive inside api: 1 and the macOS side adopts them; a page written against draft 4 keeps working.

17.1 Amendments to the shared contract

AdditionWhat it isWhy
sash.platform.family "macos" or "android". In the boot snapshot and in every sash:appearance payload. os is a bare version string; nothing else told the page which platform it is on. The page needs it for exactly one thing: the words it uses for keys and gestures. Behaviour should come from feature detection and CSS media queries, not from this field.
sash.origin The page's origin as a string: "sash://app" or "https://app.sash.invalid". So a page that must compare origins, for postMessage targets or a URL it builds for another session, never hardcodes either.
Runtime transport block An internal field of the boot snapshot telling sash.js how to send calls, how to receive events, and whether to tunnel bodies. One sash.js for both platforms. Not page-visible.
sash.ready() from the load path A rule, not a field: call it at the end of the script that boots the page, or from DOMContentLoaded, never from requestAnimationFrame or a timer chain. The update probe runs the page hidden. On Android animation frames do not fire in a hidden WebView; a page that signals ready from one would fail every probe and roll back every update.

17.2 The portability checklist

  • Pointer events, not mouse events. pointerdown, pointermove, pointerup, with setPointerCapture. Mouse events on a touch screen arrive late, compatibility-synthesised, and never for a drag.
  • Nothing that only appears on hover. A control revealed by :hover does not exist on a phone. Reveal on selection, on long-press, or always; use @media (hover: hover) to add the hover flourish where a pointer exists.
  • Say the shortcut in the platform's words. sash.platform.family === "macos" gives ⌘N; Android gives Ctrl+N when a hardware keyboard is present and nothing otherwise. Better still, name the button.
  • Hit targets of 44 CSS pixels or more for anything a finger will land on. A 6-pixel band with a 26-pixel invisible grab zone was designed for a cursor; a touch needs more.
  • Modifier keys are optional. A gesture that changes with Option or Shift needs a second gesture, or a second control, where there is no keyboard.
  • No dependence on location.host or location.protocol. Relative URLs, location.pathname, and sash.origin.
  • Insets. viewport-fit=cover and env(safe-area-inset-*) if the page draws to an edge. Sash does not pad the view; the app decides whether the page sits under the system bars.
  • Font scale. Android may scale text. Layouts that break at 130% break for real users.
  • Bodies through fetch. Not sendBeacon, not form navigation, not XMLHttpRequest, when the destination is a native route.
  • <dialog>, Intl, CSS custom properties are safe. Both engines are current.
  • Ready from the load path. See above.

17.3 What World Clock would change

The page is close. The Kotlin side of the example is the sketch in section 2. The web folder needs five edits, all of them improvements on macOS too:

  1. The scrubber and the row reordering listen to mousedown, mousemove, mouseup. Pointer events with capture, and the drag ends on pointercancel as well as pointerup.
  2. The remove button and the enlarged thumb appear on li:hover. On a coarse pointer, show the remove control on a selected row, or make swipe-to-remove the gesture, and keep the hover reveal under @media (hover: hover).
  3. The band's grab zone grows on (pointer: coarse), and the fine step that Option selects becomes a second gesture, such as a long-press before the drag.
  4. The empty state reads "Press ⌘N or the + button". It reads the family and says "Tap +" on Android.
  5. The bar at the bottom respects env(safe-area-inset-bottom).

Nothing about state, context, commands, settings, clipboard, appearance or the hour cycle changes. Those are the contract, and the contract is the same.
